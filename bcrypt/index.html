bcrypt

发表于 2026-09-28 分类于 安全

密码存数据库里，怎么存才对？常见的有三种做法:

明文存——库一泄露，密码直接裸奔。更麻烦的是多数人到处复用密码，一个站漏了，别的号全完。

用 MD5 / SHA 存——也不安全。这类哈希本来是给文件做校验用的，特点就是快。GPU 一秒能算几十亿次 MD5，配上彩虹表或字典，常见密码几秒就还原。加盐能挡彩虹表，但挡不住暴力破解，因为还是太快。

前两种有坑，问题就出在”快”上。登录慢 0.1 秒没人有感觉，可破解时每个候选密码慢 0.1 秒，成本直接从分钟涨到百年。

bcrypt 就是一种故意做慢的哈希算法。

是什么

  • 全称 bcrypt，即 “blowfish crypt”
  • 1999 年，Niels Provos 和 David Mazières，论文《A Future-Adaptable Password Scheme》
  • 底层是 Bruce Schneier 1993 年的 Blowfish 分组密码

跟 MD5 比，它多了两样东西：

  1. 随机盐。每次哈希自动生成 128 位随机盐，盐直接写在结果里。同一个密码两次哈希结果不一样，彩虹表和”整库并行破解”就废了。
  2. 成本因子。哈希时要跑 2^cost 次密钥扩展。参数可调，CPU 越强就调越大，让破解永远算不动。

因为是故意慢，也叫慢哈希或自适应哈希。

原理

bcrypt 的哈希过程分三步：

  1. 拿密码 + 随机盐做 EksBlowfishSetup。”Eks” 是 Expensive Key Schedule，昂贵的密钥扩展。标准 Blowfish 初始化密钥很快，bcrypt 把这步重复 2^cost 遍。
  2. 用派生出的密钥反复加密一个固定字符串 OrpheanBeholderScryDoubt，共 64 轮。
  3. 得到 192 位结果，拼上版本、成本、盐，就是最终的哈希。

一句话：用盐加指数级重复的密钥扩展，把一次快计算变成几百毫秒的贵计算。

哈希长什么样

拆成四段：

  • $2b$：版本
  • 12：成本因子，2^12 = 4096 次扩展
  • LQv3c1yqBWVHxkd0LHAkCO：盐，22 字符，编码 128 位
  • Yz6TtxMBJqhNnxwX5Nx3cUnYB1oGZ1C：哈希，31 字符，编码 192 位

共 60 字符。盐就在里面，验证时不用单独存盐。

版本号有讲究，这里容易踩坑：

版本 说明
$2a$ 1999 原始版
$2x$ 兼容 2011 年前的 PHP bug
$2y$ 修了 $2a$ 在 PHP 里的溢出 bug
$2b$ 现在的推荐版，修了 2011 年的截断漏洞

2011 年发现 $2a$ 对超长密码会截断，于是出了 $2b$。新项目直接用 $2b$，主流库默认就是它。

成本因子

成本因子决定哈希有多慢，取值要在体验和安全之间取平衡：

cost 迭代次数 单次耗时（大概） 场景
10 1024 50–100 ms 低风险
12 4096 200–300 ms 普遍推荐
14 16384 ~1 s 高安全

原则：调到单次 100–300ms 就行，硬件升级了再往上加。cost 每 +1，计算量翻倍。

好处是 cost 就写在哈希串里，升级是平滑的：老哈希用老参数验证，新密码用新参数生成，互不干扰。

几个坑

  1. 密码最长 72 字节。超长会被静默截断。要支持长密码，先 SHA-256 预处理一遍，或者换 Argon2。
  2. 是哈希不是加密。没法解密，所以”找回密码”只能”重置密码”，别想把原密码还给用户。
  3. 别自己拼字符串比较。用库的 checkpw / compare，内部是常数时间比较，防时序攻击。
  4. 挡不住弱密码。用户密码是 123456 的话，再强的哈希也没用。bcrypt 管的是”库泄露后难还原”，跟密码强度校验是两码事。

算法 年份 特点 现状
